# 生日測驗網頁 設計文件

日期：2026-09-08
狀態：待審核

## 一、目標與情境

做一個純前端的網頁小測驗，送給一位曖昧中的對象。她在手機上花大約五到八分鐘玩完，過程中回答興趣喜好、挑選生日慶生的餐廳、回顧兩人共同的回憶。所有答案在最後一頁送出，透過 Formspree 寄到作者的 Gmail。

慶生時間是 2026-09-11（星期五）下班後的晚餐。距離製作日只有三天，所以網頁必須當天完成並上線。

### 分寸拿捏

愛意的表達走「溫柔曖昧」路線。不直接告白，不問她願不願意，不要求她表態。核心訊息落在「你是最特別的那一個」這個力道，讓她感受得到，但保留後續空間。

### 非目標（明確不做）

- 不做後端伺服器、不做資料庫
- 不做使用者帳號、登入、權限
- 不做多語系
- 不做分享到社群的功能
- 不做管理後台，答案只寄信

## 二、體驗流程

整體是單頁應用，用 JavaScript 切換章節，沒有路由，沒有網址列變化。

### 封面

暮色背景，一朵煙火在中央綻放一次，接著浮出標題與一句邀請，底下一顆「開始」按鈕。煙火是整份網頁的開場，也是兩人共同回憶的第一個訊號。

標題、副標、按鈕文字都在 `src/data/copy.js`。這份文件不重抄一份，避免兩邊各存一份會慢慢對不上。

### 兩章問答的核心機制：互惠揭露

題目改編自 Arthur Aron 一九九七年那份「三十六個問題」的前兩組。那份研究讓兩個陌生人依序回答三十六個由淺入深的問題，四十五分鐘後產生強烈的親近感。

關鍵在於：那份研究真正起作用的不是問題本身，是**兩個人輪流揭露**。單方面的問卷只是審問，只有雙向的揭露才會產生親近感。

所以每一題都有一個 `mine` 欄位，放作者自己的答案。她一作答，作者的話就浮出來。如果她沒作答就直接按按鈕，第一次點也會先把話顯示出來，不讓她錯過。按鈕文字會從「好」變成「下一題」，跟回憶段的節奏一致。

九題的 `mine` 力道由淺到深排：從「我以前都會選最後一個，最近好像不是了」的微妙，到「我想要看穿別人在想什麼，其實只想看一個人的」的含蓄，再到「如果是在等一個人，可以先問問我有沒有空」的邀請，最後是「我的在今年四月底之後」。這句是全篇最明確的一句，位置在第二章倒數第二題，剛好在回憶段之前。

完整文字在 `src/data/questions.js`。

### 第一章：先從簡單的開始（五題）

每題一張卡，答完換下一張淡入，卡片上方的星座進度點亮一顆星。這一章刻意輕，目的是讓她願意繼續。

| 編號 | 型別 | 題目 | 選項 |
| --- | --- | --- | --- |
| q1 | 單選 | 對你來說，完美的一天長什麼樣子？ | 睡到自然醒 / 去沒去過的地方 / 跟喜歡的人待在一起 / 一個人安靜地過 |
| q2 | 滑桿 | 你覺得自己有多處女座？ | 0 到 100，兩端標籤為「完全不像」與「本人認證」 |
| q3 | 單選 | 如果明天醒來可以多一種能力，你想要哪一個？ | 睡得好 / 看穿別人在想什麼 / 瞬間移動 / 不用工作也有錢 |
| q4 | 自由輸入 | 最近有沒有什麼小事，讓你覺得今天還不錯？ | 多行文字，可留白 |
| q5 | 單選 | 如果我要送你一個東西，你比較希望是？ | 實用的 / 看得出你有在想我 / 驚喜的我不想先知道 / 什麼都好 |

q5 刻意寫成「我要送你」而不是「有人要送你」。同一題，換一個主詞，就從問卷變成預告。

### 第二章：再多知道你一點（四題）

引導文：`再問幾題。這幾題比較認真一點。`

這一章是整份問卷真正的目的。問的都是相處方式跟她自己的事，不是喜好。喜好會變，相處方式不太會。作者是摩羯座，她是處女座，這兩個星座都習慣把事情放在心裡自己消化，所以直接問比用猜的有效得多。

| 編號 | 型別 | 題目 | 選項 |
| --- | --- | --- | --- |
| d1 | 單選 | 你累的時候，比較希望旁邊的人怎麼做？ | 安靜陪著就好 / 講點好笑的讓我分心 / 問清楚發生什麼事 / 讓我自己待一下 |
| d2 | 單選 | 有沒有什麼你一直想做，但一直還沒去做的事？ | 有但沒時間 / 有但有點不敢 / 有，在等一個人一起 / 好像沒有耶 |
| d3 | 單選 | 你最珍貴的那段回憶，大概是什麼時候？ | 小時候 / 學生時代 / 出社會之後 / 最近這一年 |
| d4 | 單選 | 講真的，你覺得我是哪種人？ | 想很久才會行動 / 話不多但講了就會做 / 有點難懂還在觀察 / 比看起來的更在乎細節 |

d2 改編自 Aron 的第十四題。第三個選項「在等一個人一起」是刻意放的，作者的回答是「如果是在等一個人，可以先問問我有沒有空」。不管她選哪一個，那句話都成立。

d3 改編自第十七題。作者的回答是「我的在今年四月底之後」，也就是他們認識之後。這是整份網頁講得最明白的一句。

d4 是唯一一題問她怎麼看作者的，四個選項都是摩羯座的典型樣子。她選哪一個，作者都能知道自己在她眼裡是什麼形狀。

d1 有立即用途，它決定生日那天的節奏該熱鬧還是安靜。

### 過場：我們的星圖（五顆星）

深入題結束後進入回憶段。畫面上五顆星依序解鎖，前四顆各配一題小回憶題，答完才浮現作者的話。答錯不扣分、不重來，只是換一句回應。

| 星 | 題目 | 型別 | 正解 |
| --- | --- | --- | --- |
| s1 | 我們第一次見面，是在做什麼？ | 單選 | 桌遊店 |
| s2 | 後來我們去吃了蛋糕。你還記得那是什麼樣子嗎？ | 自由輸入 | 無正解，寫什麼都給同一段回應 |
| s3 | 我們一起看過幾次煙火？ | 單選 | 兩次 |
| s4 | 是哪兩個地方？ | 複選 | 大稻埕、淡水 |
| s5 | 不設題 | — | 直接顯示作者的話 |

s4 揭曉時放一朵煙火。s5 顯示完，星座線把五顆星連起來，動畫結束後進入下一章。

答對與答錯的回應文字都在 `src/data/memories.js`。這一段是整份網頁情緒最重的地方，寫作原則有三條：

第一，寫作者自己的感受，不寫她當時做了什麼。虛構她的動作她一眼就看得出來，會毀掉整段。

第二，答錯的回應要跟答對一樣溫柔。她答錯的機率不低，那一刻不能讓她覺得自己失分了。

第三，每段話收在一個具體的畫面上，不收在形容詞上。「走出店門的時候覺得這個晚上結束得太快」比「那天很開心」有效得多。

### 第三章：生日餐桌

開場直接講明這是在安排她的生日，並且說清楚是先問她想去哪，而不是自己決定好再通知。這個差別很重要，它決定了整章讀起來是邀請還是通知。開場文字在 `src/data/restaurants.js`。

**餐廳卡片（五張，可複選並記順序）**

全部在竹圍，走路可到。原本混了幾間淡水站的河景餐廳，後來全部換掉，因為那裡是他們熟悉的地方，而下班後多一段車程就多一分趕。之間茶食器也因此出局，它在淡水老街尾端。

每張卡包含一個線條圖示、店名、一句描述地點與類型的話，以及一句作者寫的推薦理由。

地點與類型寫成一句自然的中文，不用中點串接。`竹圍站旁的韓式湯飯` 讀起來像人話，`竹圍站旁 · 韓式湯飯` 讀起來像資料庫欄位。

卡片上不顯示價位。作者選這幾間時已經把預算篩過一輪，把價位攤在她面前只會讓她挑便宜的那間，而不是挑想去的那間。

| id | 店名 | 地點與類型 | 圖示 | 推薦理由（可改） |
| --- | --- | --- | --- | --- |
| pinwei | 品味牛排餐酒館 | 竹圍站旁，民族路二樓的牛排餐酒館 | glass | 這間最有慶生的感覺，牛排是真材實料。位子不多，我會先訂 |
| heishi | 黑市shabu 竹圍店 | 民族路上走三分鐘的鍋物 | pot | 昆布湯底不加味精，菜盤都是原型食材。二樓是四人桌，安靜好講話 |
| kimchunhee | 金春喜韓廚 竹圍店 | 捷運站旁的韓式湯飯 | bowl | 離我們熟悉的地方最近，小菜白飯霜淇淋無限續，可以慢慢吃慢慢聊 |
| gwangju | 光州神仙爐 | 竹圍站走三分鐘的韓式小鍋 | lid | 一人一鍋，部隊鍋豆腐鍋都有。用餐時間常客滿，在地人是真的愛 |

四間實店的價位由高到低排，類型也各自區隔：西式餐酒館、鍋物、韓式湯飯、韓式小鍋。品味牛排均消約八百且只開到晚上九點半，位子少必須訂位。黑市 shabu 均消四百到六百，Google 四點七，一樓是吧檯，二樓才是四人桌。

原本還有肉老大涮涮鍋與好菜園台菜，作者後來拿掉了。

光州神仙爐均消只有一百，比作者說的預算下限還低。它留下來是因為作者指定它保底，而「保底」跟「不要太便宜」這兩個要求衝突時，該由作者決定，不是實作者自己刪掉。這件事值得記下來：需求互相矛盾的時候要問，不要自己選一邊。

圖示用行內 SVG 畫，未選取時是淡的紙白線條，選取後轉成煙火桃並發光。

**每張卡下面有一個地圖連結**。作者沒有這些店的照片授權，熱連結對方網站的圖片也會破圖，所以改成給連結：`mapLink()` 用店名加地址組出 Google 地圖的搜尋網址，她點開就看得到照片、評價、地址與營業時間，比放一張自己拍不出來的照片有用得多。

連結必須是按鈕的兄弟元素，不能包在按鈕裡面，否則會變成互動元素巢狀，鍵盤與螢幕閱讀器都會出問題。所以每張卡的結構是一個 `.opt-row` 容器，裡面一個選取用的按鈕加一個連結，底線畫在容器上。連結一律開新分頁並加 `rel="noopener noreferrer"`，不能讓她點一下就離開這一頁把答案弄丟。

營業時間與價位以 2026-09-08 查得的網路資料為準，實際訂位須另行電話確認。竹圍漁港旁那間「賜福船長的店」查證後在桃園大園，不是淡水竹圍，已排除。

**這一章只有一題，但可以複選，而且記順序。**

她點的第一間就是第一順位，卡片左邊會出現名次。再點一次取消，後面的名次自動遞補。理由很實際：禮拜五晚上熱門的店訂不到，作者需要一份可以照著往下打電話的清單，而不是一個選擇加一個備案。原本拆成兩題問第一選擇與備案，換成排序之後既少一題，拿到的資訊又更多。

「都可以，你決定就好」跟其他四間互斥。選了它就清空其他，選其他就把它移除。兩者同時成立沒有意義。

排序存成 `state.dinner.ranked`，是一個店家 id 的陣列，順序就是她的順序。

原本這裡還有幾點吃、要不要蛋糕、安靜還是熱鬧三題，後來拿掉了。理由是這些細節作者當面問一句就有答案，而每多一題，整份問卷就多一分「填表單」的味道。同樣被拿掉的還有未來清單與留言，它們讓結尾拖得太長，稀釋掉了最後那段話的力道。

拿掉的代價要講清楚：作者拿不到她偏好的時間、要不要蛋糕、想安靜還是熱鬧。這三件事得自己開口問。這是刻意的取捨，不是遺漏。

### 結果頁

由上往下是三塊：專為截圖設計的結果卡、給她的話、送出按鈕。按下送出之後畫面換成結束語，加上一顆用方程式畫出來、正在跳的心。

**結果卡規格**

這張卡是保存的第二道保險。就算 Formspree 出問題、就算她沒按送出，只要她截圖傳過來，作者要的資訊一樣拿得到。所以卡片必須自己站得住，不能依賴頁面其他部分。

- 版面比例貼近手機直式，一屏之內截得完，不需要捲動也不需要拼接
- 卡片有明確的邊界與外圍留白，截圖不會切到旁邊的元素
- 最上面是一朵由生日日期算出來的花，作為這張卡的圖騰
- 花下面是 `{她的名字} 的小檔案`
- 接著星圖時間軸橫過卡片：四月底桌遊店、蛋糕、大稻埕、淡水、現在，末端一個未點亮的光點，標註 `下一顆，等你`
- 中段是她排在第一順位的餐廳，用整張卡最大的字級。這是作者最需要看到的一項，底下一行小字照順序列出其餘幾間
- 下段是性格摘要，寫成一句話而不是表格，例如 `八十分的處女座，累的時候想要有人安靜陪著`。這句由處女座滑桿與 d1 的答案組成
- 卡片底部一行淡色小字寫日期，格式是 `2026.09.11`

卡片刻意只留這幾項。題目砍掉之後如果還硬要湊出對照列，卡片會變成一張稀疏的表格，那比空著更糟。

卡片下方放一行輕聲的提示：`截圖傳給我也可以`。不做「存成圖片」按鈕，那需要額外的函式庫，而截圖本來就永遠可行。

**給她的話**

全文在 `src/data/copy.js` 的 `CLOSING`。分寸抓在「讓她知道自己很特別」，不推進到「所以你要給我一個答案」。最後一句留在生日那天，而不是留在關係的定義上。

**兩件用數學做的東西**

作者是工程師，所以這份網頁裡有兩個地方是真的在算，不是把公式當裝飾。一個是結果卡上靜態的圖騰，一個是送出之後的壓軸。

第一個是結果卡頂端那朵花，程式在 `src/js/rose.js`。極座標玫瑰線 `r = cos(n/d · θ)`，月份放分子、日期放分母。當兩個都是奇數，曲線在 `dπ` 之內閉合，長出 `n` 片花瓣；只要有一個是偶數，就得繞到 `2dπ`，花瓣加倍。九月十一號兩個都是奇數，所以長出九片。換一個日期，形狀就不一樣，這朵花只屬於這一天。花瓣數有測試釘住，算錯的話這個設計就沒有意義了。

結果頁原本還有第三個，兩條逐漸同步的 Kuramoto 耦合振盪器波形，耦合強度綁在她的作答完成度上。後來拿掉了。它自己是漂亮的，但它跟結尾那段話搶版面，而且需要一句話解釋才看得懂。需要解釋的東西放在告白前面就是雜訊。

第二個是心臟線，程式在 `src/js/heart.js`。從結果頁就開始跳，送出成功之後同一顆心留在畫面上，動畫沒有中斷過，只是被搬到新的版面裡。

```
r = a(1 − sin θ)
```

笛卡爾在十七世紀寫下的極座標曲線。從 `θ = π/2` 起筆，因為那個角度 `r = 0`，正好是心形凹進去的那一點，所以整顆心是一筆畫完的，不是拼出來的。

描完之後轉成脈動：`a` 隨時間微幅變化，節奏用兩個高斯脈衝疊出來，一下重一下輕，模擬心跳的 lub-dub，週期約每分鐘五十七下。

這裡原本做成五格輪播，用方程式一格一格描出 L、O、V、E，最後才是心。後來拿掉了，只留心。四個字母是在解釋一件不需要解釋的事，而且它們把最後那顆心的位置往後推了七秒。一個東西要當壓軸，前面就不能先放四個同類的東西暖場。

位置在結尾那段話的正下方。原本設計成只有送出成功才出現，理由是「放在最後才有力量」，但那代價太大：她如果沒走到那一步、或送出失敗走了備援，就完全看不到這顆心。一個看不到的壓軸不是壓軸。現在它在結果頁就跳，前面兩章的克制已經夠了，不必再靠延後出場來累積。

心形下方只放一行方程式，不加任何說明文字。她會問那是什麼，那就是作者開口的機會。

繪製一律延到下一幀才做。剛把 canvas 放進版面的時候寬度還是零，那一幀畫出來的心會落在錯的位置。關閉動態的路徑只畫一次，所以這個延後對它來說是必須的，不是保險。

底部一顆送出按鈕。送出成功後畫面換成結束語加這顆心，結果卡留在畫面上，讓她還能截圖。

## 三、技術架構

純靜態網頁，沒有後端，沒有建置流程。直接用瀏覽器原生的 ES modules，開啟 index.html 就能跑。

### 資料流

1. 使用者每答一題，答案寫入記憶體中的 state 物件
2. state 每次變更同步寫入 `localStorage`，key 為 `special-website-v1`
3. 頁面重新載入後按下開始，直接沿用 localStorage 裡的答案接續作答，不另外詢問。少一道讓她困惑的門檻
4. 結果頁按下送出，把 state 序列化成 JSON，用 `fetch` POST 到 Formspree endpoint
5. Formspree 把內容寄到作者的 Gmail

### 送出失敗的備援

網路失敗或 Formspree 回非 2xx 時，顯示錯誤訊息與兩個按鈕：

- `再試一次`：重送
- `複製答案`：把答案整理成純文字複製到剪貼簿，讓她可以直接貼訊息傳給作者

這個備援是必要的。只有一次機會，不能因為一個網路錯誤就全部白費。

### 送出的資料格式

```json
{
  "submittedAt": "2026-09-09T13:05:00+08:00",
  "about": { "q1": "...", "q2": 80, "q3": "...", "q4": "...", "q5": "..." },
  "deeper": { "d1": "...", "d2": "...", "d3": "...", "d4": "..." },
  "memories": { "s1": "桌遊店", "s1Correct": true, "s2": "...", "s3": "兩次", "s3Correct": true, "s4": ["大稻埕", "淡水"], "s4Correct": true },
  "dinner": { "ranked": ["黑市shabu 竹圍店", "品味牛排餐酒館"] }
}
```

Formspree 的信件主旨設為 `她填完了`，方便在 Gmail 一眼找到。

### 檔案結構

```
index.html

    base.css          重置、CSS 變數、字體
```

純邏輯與畫面操作分開。state、payload、summary 三個檔案不碰 DOM，所以可以直接用 Node 執行測試。render、flow、result、starmap 負責畫面，不含商業邏輯。

所有文字內容集中在 `src/data/`。之後要改題目或換餐廳，只動那幾個檔案，不碰程式邏輯。

每個 js 檔只負責一件事，檔案之間透過明確的 export 溝通。state.js 不知道畫面長怎樣，render.js 不知道資料怎麼存。

## 四、視覺設計

主題是淡水的傍晚到夜，不是外太空的星空。手機優先。

這個區別很重要。深藍底配單一金色是目前生成式設計最常見的樣板之一，看起來像任何一個科幻產品頁。而這份網頁的世界是具體的：淡水河、對岸的燈、兩場煙火、一頓晚餐。所以背景是一整片暮色漸層，底部留著地平線的餘光，那是他們看煙火時對岸的燈火。

### 色彩

| 用途 | 色碼 |
| --- | --- |
| 深靛（天頂） | `#14203B` |
| 暮紫（天空中段） | `#3B2F52` |
| 地平線餘光 | `#6B4A63` |
| 紙白（主文字） | `#FBF3E7` |
| 河霧灰藍（次文字） | `#93A4C4` |
| 煙火桃（選取狀態） | `#FF6F91` |
| 燈籠黃（主要動作） | `#FFC94A` |

兩個強調色各有職責，不混用。煙火桃只用在她選了什麼，燈籠黃只用在往前走的動作與作者說的話。

### 字體

全站宋體，不用黑體。這本質上是一封信，宋體的筆畫有溫度，黑體沒有。

中文用 Noto Serif TC，西文與數字用 Cormorant Garamond。兩者氣質接近，混排不打架。字體變數要注意順序，通用的 `serif` 只能放在整串的最後面，放在中文字體之前會讓中文永遠拿不到指定的字體。

內文十七像素，行高一點九。宋體筆畫細，需要比黑體更寬鬆的行距才好讀。

### 背景的六層

第一版的背景是一整片靜止的漸層加五顆同步呼吸的星點。問題有三個：五顆星同時亮同時暗，看起來是螢幕在明滅不是星星在閃；大面積的平滑漸層在手機的 OLED 上會走色帶，讀起來像色票不像天空；最重要的是主題明明是淡水河邊，畫面裡卻沒有河，底部那道暖光懸在半空，下面沒有東西承接它。

重做成六層，由後往前：

| 層 | 內容 | 動的東西 | 週期 |
| --- | --- | --- | --- |
| 底 | 暮色漸層 | 不動 | — |
| 一 | 色溫，天空在暖與冷之間來回 | `opacity` | 96 秒 |
| 二 | 對岸的兩團燈火 | `transform` | 54 與 71 秒 |
| 三 | 兩層可平鋪的星空，各自往上飄 | `transform` | 96 與 210 秒 |
| 四 | 遠方的煙火，天邊安靜開一朵 | `transform` 與 `opacity` | 46 與 61 秒 |
| 五 | 河，底下三分之一 | `transform` | 38 秒 |
| 六 | 顆粒 | 不動 | — |

**只動 `transform` 與 `opacity`。** 這兩個屬性能純粹跑在合成器上，主執行緒再忙也不掉幀。明確不做的有三件，每一件都是網路上常見但會在中階手機掉到三十幀以下的做法：動 `background-position` 掃全螢幕漸層（每幀重新光柵化整個視窗）、用 `@property` 動漸層的色停點（每幀重畫背景）、即時跑 SVG 的 `feTurbulence`（CPU-bound，會發燙）。

**不用 `filter: blur()` 做大面積柔光。** 大半徑模糊每個輸出像素都要採樣更大範圍，四百像素以上的元素應該把半徑壓在二十以下。柔邊改用四段漸出停點的 radial-gradient，視覺幾乎一樣，成本是零。唯一用到 blur 的是河面倒影，半徑八像素、範圍限制在河的上半部。

**星空的週期用除不盡的比例。** 兩層用 96 與 210 秒，兩群星點用 9 與 13 秒，這樣才不會每隔幾輪就重合成「整層一起閃」。可平鋪的做法讓星星變多但成本不變：位移剛好一個 tile 的高度就無縫接回。

**河是這一版最重要的補充。** 水是唯一能名正言順地一直動的表面，因為人本來就預期水在動。真實的倒影是縱向拉長、被橫向波紋切斷的，所以做法是把地平線的暖光鏡射下來、`scaleY(-1.7)` 拉長，再疊一組橫向細線極慢平移把它切斷。兩個廉價的假動作疊起來大腦就認了，不需要模擬流體。

**顆粒是投報率最高的一層，而且完全靜態。** 一張 140 像素見方的雜訊貼圖，`stitchTiles` 讓平鋪看不出接縫，疊在最上層、透明度 0.045、混合模式 overlay。它同時解決色帶，也讓整片天空從色票變成有微粒的空氣。雜訊是渲染一次的貼圖，不是即時濾鏡。

**一艘渡輪每隔九十六秒橫渡一次。** 桌機上內容欄兩側會留白，那裡需要一個東西。選渡輪不選裝飾圖案，是因為它屬於這個地方：淡水的船就在那條河上。船身是一張四十八像素寬的 SVG 剪影，只有窗是暖色的，底下拖一道船燈在水面的反光。負的動畫延遲讓她一打開就看得到船已經在河上，不用等一分半。

沒有選愛心或情人節元素，因為前面所有的克制都是為了讓最後那顆心有力量，提前放會爆雷。也沒有選貓咪之類的可愛角色：它本身沒有問題，但它不屬於這個故事，畫面會變成「淡水的夜」加上「一隻貓」，兩件事各自成立卻湊不起來。

**遠方的煙火每隔快一分鐘開一朵**，一朵是一個元素加八個 `box-shadow` 的點，`box-shadow` 本身不做動畫，只動 `transform` 與 `opacity`。峰值透明度 0.45，位置在畫面上三分之一且避開正中央，不跟文字打架。

`prefers-reduced-motion` 不能只靠全域把 `animation-duration` 設成 0.01 毫秒，那會讓動畫凍在隨機的一幀。背景層另外寫了一組規則，明確指定靜止時該是哪一格。

### 其他元素

- 沒有卡片。題目是一段文字，選項是細線分隔的清單，選取時左邊亮起一顆煙火桃的小點
- 餐廳選項用線條圖示取代小點，選取時圖示變成煙火桃並發光
- 主要動作是細框方角按鈕，不是圓角膠囊
- 進度是一段星座，點的位置刻意不等距。等距會看起來像進度條，不像星圖
- 星座線在回憶段結束時一次連起來，這是視覺上的高潮
- 封面有一朵綻放一次的煙火，淡水大稻埕那題揭曉時再放一次。全站只有這兩處非使用者觸發的動態
- 結果卡是整站唯一有邊框的元素。因為它真的是一張要被截下來的卡，邊框在這裡是功能，不是裝飾

### 動態

所有轉場控制在三百毫秒以內。尊重 `prefers-reduced-motion`，使用者若關閉動畫則只做淡入淡出。

### 手機相容（硬性需求）

連結會直接傳到她的手機，她多半在通訊軟體裡點開。手機上跑不順就等於失敗，所以下列每一項都是必須，不是加分項。

- 從三百七十五像素寬開始設計，再往上放大。桌機版是附帶，手機版是主體
- 所有可點擊的元素，觸控範圍至少四十四乘四十四像素
- 內文字級不小於十六像素。輸入框的字級也必須到十六像素，否則 iOS Safari 會在聚焦時自動放大整頁
- 版面高度用 `100dvh` 而不是 `100vh`，避免行動瀏覽器網址列伸縮造成畫面跳動
- 不把 hover 當成唯一的互動提示，觸控裝置沒有 hover
- 直式為主，橫式轉向不能壞掉，至少要能正常捲動閱讀
- 星空與煙火動畫必須在中階手機上維持順暢。粒子數量要設上限，掉幀就減量
- 字體透過 Google Fonts 載入，但必須設定系統字體備援，並用 `font-display: swap`。她可能在行動網路下開啟，不能因為字體沒載完就整頁空白。兩套字體各只載兩個字重，中文字體多一個字重就是多一整套子集，那才是真正吃頻寬的東西，不是背景
- 不放大圖。所有視覺用 CSS 做，整站資源總量控制在一兩百 KB 以內
- 通訊軟體的內建瀏覽器（LINE、Instagram、Messenger）也要能正常運作，因為她很可能不會另外用 Safari 或 Chrome 開

最後這點特別重要。通訊軟體的內建瀏覽器限制較多，測試時要實際在 LINE 裡點開一次。

### 聲音

一開始的非目標寫著不做音效與背景音樂，後來作者改變主意，要一個很小聲的水聲。這是對的決定，主題本來就在河邊。

**沒有音檔。** 聲音是用瀏覽器內建的音訊合成即時算出來的，程式在 `src/js/ambience.js`。

第一版做成「白噪音通過低通濾波器，音量緩慢起伏」，聽起來像風不像浪。差別在於風是連續的，海浪是一次一次的事件：碎波的瞬間有爆發，泡沫的高頻嘶嘶聲跟著出來；接著拖長衰減，高頻先消失，最後只剩低頻的隆隆聲；隔幾秒再來一次，間隔與強度每次都不一樣。

所以現在有兩條路徑。一條是持續的低頻底噪，截止頻率壓在一百八十赫茲，那是遠處的海一直在那裡。一條是碎波，每隔六到十二秒觸發一次，音量與濾波器亮度共用同一段包絡，而且亮度衰減得比音量更徹底。

**「高頻比低頻先消失」是聽起來像水而不像風的關鍵。** 每次碎波的間隔、上升時間、衰減長度、峰值與亮度都在一個範圍內隨機，而且左右聲道位置也隨機偏移，海才有寬度不會像一個點在響。

不用音檔有三個理由：一首背景音樂至少幾百 KB，行動網路上她要等；作者沒有任何音樂的授權；而合成的成本是幾 KB 的程式碼。

**音量預設 0.06，而且一律用三秒的斜坡淡入。** 突然出聲跟突然斷掉一樣會嚇到人。開關切換時也是斜坡，不是直接跳。

**必須有關閉鈕，這不是加分項是硬性要求。** 無障礙標準要求任何自動播放超過三秒的聲音都要能停。按鈕固定在右上角，四十四像素見方，開著的時候是兩道波浪，關掉之後變成一道加一條斜線。她的選擇存進 `localStorage`，下次打開會記得。

**啟動時機只有一個。** 瀏覽器一律擋掉沒有使用者手勢的有聲播放，所以聲音只能在她按下封面的「開始」之後才開始。這也剛好是對的時機，封面那一刻應該是安靜的。

分頁切到背景時暫停音訊環境，回來再繼續。她可能中途去回訊息，不能讓聲音在背景一直跑。

如果瀏覽器不支援音訊合成或建立失敗，按鈕直接隱藏，不留一個按了沒反應的東西在畫面上。

## 五、部署

用 Netlify Drop，把整個資料夾拖進去就有一個公開網址，免費，不用綁網域，不用帳號設定。

網址不做密碼保護。理由是多一道門檻會讓她卡住，而內容本身沒有隱私風險。

## 六、測試

純邏輯的部分用 Node 內建的測試執行器驗證，指令是 `node --test tests/*.test.js`。不需要安裝任何套件，也不影響網頁本身維持零依賴。狀態存取、送出的 JSON 組裝、結果卡的文案組裝這三個模組都要有測試。

畫面與互動沒有自動化測試，用下面的手動清單驗證：

手機測試排在最前面，因為那是她實際使用的裝置。

1. 用真手機完整跑一次，確認版面、字級、觸控範圍、動畫順暢度
2. 在 LINE 裡貼上網址點開，完整跑一次。這是最接近她真實情境的測試
3. 結果卡在手機上截圖一次，確認一屏截得完、內容不被切到
4. 中途關閉再打開，確認接續作答正常
5. 送出一次，確認 Gmail 真的收到信，且欄位完整可讀
6. 斷網後按送出，確認錯誤畫面與複製答案的備援可用
7. 桌機 Chrome 跑一次，確認沒有明顯破版
8. 開啟系統的減少動態效果設定，確認動畫降級正常

第一、二、五項必須在把網址給她之前實際做過。

## 七、開工前需要作者提供

五顆回憶星、結尾那段話、封面副標的完整文字都在 `src/data/` 裡，以那裡為準。以下是還沒補上的：

1. 她的名字或暱稱，用在封面與結尾
2. 作者的署名方式，或不署名
3. Formspree 的 form endpoint：存在 `src/data/config.js`，那個值不進版本庫
4. 桌遊店的店名，若想寫進回憶文案
5. 六張餐廳卡的推薦理由是否要改成作者自己的話
6. 結尾那段話是否照用，或要改字

## 八、時程風險

慶生在 2026-09-11 晚上，只剩三天。網頁本身當天可以完成，真正的風險在餐廳訂位。週五晚上的熱門餐廳現在就可能滿了。

建議的順序是：作者今天先打電話問兩間，能訂就先訂可取消的；網頁今晚給她玩；她的選擇當作確認而不是決定。這樣兩邊都不會落空。
